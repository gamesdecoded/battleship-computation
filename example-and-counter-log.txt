2. COUNTER-SEARCH — RANDOM VS EDGE-AWARE, SAME SEARCHER
================================================================
Definition (round-1 definition, re-implemented here): edge-aware
density is group-all marginal placement-count, except that, per
ship, only placements that touch at least one board edge
(row 1 or 10, or column 1 or 10) are counted. It is the searcher
that knows the hider hides on edges, and only considers
edge-touching placements.
Sample: 2,000 random placements and 2,000 edge placements,
same sample size as the round-1 edge-aware run (2,000 per
strategy), fresh seed 20291120, same placement definitions as
production (random: uniform legal placement; edge: every ship
touches at least one board edge).

Results, mean shots to sink (higher = better hiding):
  Random placements vs edge-aware searcher:
    72.19, median 75.0, SD 11.67, 95% CI +/-0.51 (n = 2,000)
  Edge placements vs edge-aware searcher:
    32.84, median 33.0, SD 4.69, 95% CI +/-0.21 (n = 2,000)
  Unpaired difference, edge minus random, same searcher:
    -39.35, 95% CI +/-0.55
Reproduction check: edge vs edge-aware here is 32.84, against
round-1's 32.97 on its own 2,000-placement sample. Consistent.
Claim now supported, same searcher, same sample sizes:
  Against an edge-aware searcher, an edge fleet (about 33 shots)
  sinks far faster than a random fleet (about 72 shots).
  Edge hiding is worse than a random fleet against that searcher.
Claim NOT used (it mixes searchers, as Decoder flagged):
  Comparing edge vs edge-aware (32.84) with random vs plain
  density (44.68, verified core) or random vs line-bonus
  (44.68, verified core) — those are different searchers and
  must not be compared as if they were one test.
Why random survives so long against the edge-aware searcher:
  the searcher only counts edge-touching placements, so it
  spends its early shots on the edges while a random fleet's
  ships, which are usually not all on edges, sit elsewhere.
  That is the cost of a searcher that commits to one hiding
  theory. It is stated as the mechanism of the test, not as
  a claim about real human opponents.

3. DROP-RULE DEFINITION — ORIGIN-ONLY, MEASURED
================================================================
Script v2 defines the drop rule as: when a ship sinks, drop only
the targets that ship created. A target that was also created by
a different, still-unsunk hit is kept, even if it touches the
sunk ship. That is the definition Decoder required, because
ships may touch: a target touching a sunk ship can also be a
neighbour of another unsunk hit, and the old wording ("drop
every target touching it") clashed with "keep targets for a
different unsunk hit" in exactly that case.
Measured check, 10,000 fresh fleets, seed 20291120:
  Centre-out rule, clear-adjacent version (the version in
  verified-core.txt: drop stack entries adjacent to sunk cells):
    54.35, median 54.0, SD 10.26, 95% CI +/-0.20
  Centre-out rule, origin-only version (drop a stack entry only
  if every ship that generated it is the sunk ship):
    54.31, median 54.0, SD 10.18, 95% CI +/-0.20
  Paired difference, origin-only minus clear-adjacent:
    -0.04, 95% CI +/-0.03
Reading: the origin-only wording describes the measured rule to
within four hundredths of a shot. Script v2 therefore uses the
origin-only definition, and quotes the verified clear-adjacent
numbers (best human 54.45, verified core, 10,000 fleets, seed
20291110; paired saving 6.72 against the verified baseline
61.18). The 0.04-shot difference is not a new headline and is
not quoted as one in the script.
Spacing rule wording, corrected as Decoder required: the hunt
widens as the smallest ship still afloat grows — after the
two-square ship sinks, hunt every third square; after the
three-square ships sink, hunt every fourth square. It is NOT
"after the smallest sinks" without saying "still afloat",
because the rule keys on the smallest ship that has not sunk.

   used; it is geometrically impossible as written.

5. CENTRE-OUT HUNT ORDER (from code, for v3 Ch8)
   advanced2.py play_human, hunt_mode='centre_parity': candidates are
   black squares only, (row+col) % 2 == 0, sorted by DIST2 then row-major
   index q. engine.py DIST2 = (row-4.5)^2 + (col-4.5)^2 (0-indexed).
   In 1-indexed rows/cols, first squares in order: row 5 col 5, row 6 col 6,
   row 4 col 6, row 5 col 7, row 6 col 4, row 7 col 5, then row 4 col 4,
   row 7 col 7, and so on, nearest to the centre first, ties by earlier
   row then earlier column. This order IS precisely statable and
   reproducible, so v3 keeps centre-out as the named best human rule
   (task option a) and the printed diagram is a drawing of this order,
   not an extra rule and not a count table.
